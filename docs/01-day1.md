## Theory card 1: CI, delivery, deployment

**Continuous integration** validates code changes automatically. A useful CI process
checks the actual revision, reports errors, and blocks later steps when required checks
fail. It does not mean “a script runs somewhere.”

**Continuous delivery** prepares a verified release and may require a human decision to
deploy. **Continuous deployment** deploys every eligible change automatically. Day 1 is
CI; Day 2 uses a human approval and is a continuous delivery exercise.

Pipeline flow today: checkout → dependency installation → lint → tests → evidence.
An artifact is a saved output, such as JUnit XML. A workspace is the temporary build
directory. A Git commit identifies source; a Jenkins build number identifies an execution.

Ask: “If tests fail, should publishing still run?” Expected: required tests stop delivery;
diagnostic reports should still be published in `post { always { ... } }`.

### Walkthrough: why the code is structured this way

`normalize_title` in `service.py` is pure logic: it trims whitespace, checks type, and
enforces a 1–120-character limit. Test it without HTTP or a database.
`create_app` constructs an isolated application. Tests override its database path;
this avoids accidentally testing against the developer's actual data.
Each request opens a database connection only when needed and closes it during teardown.
Writes use parameter placeholders, not string-concatenated SQL. The injection test shows
why a suspicious task title must remain data.

The health endpoint checks the database table, not only the Python process. The version
endpoint proves which release is running. Discuss why process-up and service-ready are
different observations.

## Lab 1B: tests students actually understand

```bash
.venv/bin/python -m pytest tests/test_api.py -v
.venv/bin/python -m pytest tests/test_api.py -k invalid_title -v
.venv/bin/python -m pytest tests/test_api.py -k persistence -v
```

Expected: passing tests, a selected validation subset, and a persistence test.
`-k` filters test names. `-v` prints individual results. Tests create temporary databases
using `tmp_path`; running the suite must not create or delete production tasks.

### Theory card 2: test layers

| Layer | Here | What it catches |
|---|---|---|
| Unit | `normalize_title` tests | Incorrect validation or boundary logic |
| API/database integration | Flask client + actual temporary SQLite | Route, JSON, SQL, and persistence mistakes |
| Automation tests | Mocked Docker/HTTP boundaries | Wrong release/recovery decisions |
| Smoke, Day 2 | Real running HTTP service | Startup, readiness, routing, or version problems |

The Flask test client does not start a network listener. It exercises the application
inside the test process. Mocked Docker tests validate decision logic; they cannot prove
that a real Docker deployment works. Day 2 must verify that separately.

## Lab 2: lint, coverage, and evidence

Run in this order:

```bash
.venv/bin/python -m ruff check app scripts tests
.venv/bin/python -m pytest --junitxml=reports/junit.xml --cov=app --cov=scripts --cov-report=xml:reports/coverage.xml --cov-report=term-missing --cov-fail-under=80
ls reports
```

Expected: lint passes, tests pass, coverage meets 80%, and XML files exist.
Do not type `--cov= scripts`: the space can turn the module name into a separate argument.

### Theory card 3: coverage and exit codes

Coverage measures which code was executed, not whether the assertions are meaningful.
A test that calls a function without checking its output may increase coverage without
protecting behavior. The 80% threshold is a teaching gate; improve assertions as well.

An exit code of 0 usually means success; nonzero means failure. Jenkins `sh` treats
nonzero as a failed step. Never append `|| true` to required tests to obtain a green build.
JUnit XML is a report format, not a requirement to write Java tests. Jenkins' JUnit plugin
can display pytest results in that format. Coverage XML is archived here; a coverage
visualization plugin is optional and not required for the gate.

Challenge: temporarily run `--cov-fail-under=100`. Explain any failure. Restore 80 after
the exercise. Do not lower the gate to hide a regression.

## Lab 3: create the Jenkins job

First publish/fork the repository using the integration guide. Alternatively the instructor
provides a reachable Git repository. A folder existing on the laptop is not automatically
available to Jenkins on the VM.

1. Jenkins → New Item → name `workshop-day1` → Pipeline.
2. Definition: Pipeline script from SCM. SCM: Git.
3. Repository URL: your real workshop URL. Add checkout credentials if private.
4. Branch specifier: `*/main` (replace if your branch differs).
5. Script Path: `pipelines/Jenkinsfile.day1`.
6. Save → Build Now. Open Console Output and follow each stage.

For the teaching exercise, use the reference file to guide students as they add the
checkout, preparation, lint, test, and post sections one at a time in a working branch.
Commit and push after each meaningful stage. The instructor can initially create a
Pipeline job for that branch, then switch its branch specifier to main after review.

### Theory card 4: read the Jenkinsfile

`agent { label 'workshop-linux' }` chooses where commands run. A matching offline node
leaves the job waiting; it is not a Python failure.
`checkout scm` retrieves the repository revision. `skipDefaultCheckout(true)` prevents
an extra automatic checkout.
`sh` executes on Linux. Use `bat`/PowerShell and different environment paths for a
Windows agent; that is a different pipeline, not a text substitution inside these labs.
`timeout` limits hung builds, and `disableConcurrentBuilds` serializes runs of this job.
`post { always { ... } }` records available evidence even after a failure.
`deleteDir()` removes workspace files after archiving; it does not delete the Docker
volume. `allowEmptyResults` allows a failure before tests to preserve the original failure
without an extra missing-report error. It does not make failed tests pass.

Pipeline-as-code puts release logic under review alongside application code. Official
references: [Using a Jenkinsfile](https://www.jenkins.io/doc/book/pipeline/jenkinsfile/),
[recording tests and artifacts](https://www.jenkins.io/doc/pipeline/tour/tests-and-artifacts/).

## Lab 4: deliberately fail CI and diagnose it

Create a practice branch:

```bash
git switch -c lab/day1-failure
```

In `app/service.py`, change `title = value.strip()` to `title = value`. Then:

```bash
.venv/bin/python -m pytest tests/test_api.py -k normalize_title -v
git add app/service.py
git commit -m "lab: demonstrate whitespace validation regression"
git push -u origin lab/day1-failure
```

Configure a separate practice job to build this branch. Expected: lint may pass, but the
test fails. Find the expected/actual title, test name, and commit in Jenkins. Restore the
line to `.strip()`, commit the fix, push, and observe a green build. Keep the broken commit
on the practice branch; do not merge it into main.

Independent exercise: add a test for an API feature, such as rejecting an oversized title
through POST, and show that it would detect a deliberately introduced bug. Submit the
test and the corrected implementation, not the bug.

## Submission and exit questions

Submit repository URL or Git commit, successful build URL, failed build URL, and a short
explanation of the failure. Show JUnit results and coverage evidence in Jenkins.

Answer: Where do builds execute? Why keep reports after failure? What is the difference
between a unit test and a real HTTP smoke test? What does coverage fail to prove?
If the agent goes offline, which part of the system should you inspect first?
