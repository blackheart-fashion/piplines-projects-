# Day 2 — automated delivery, verification, and recovery

## Outcomes and scope

Students deliver a tested Docker image to a dedicated Linux host, inspect the exact
running release, reject an unhealthy candidate, and explain recovery after a failed
cutover. Registry publication and delivery to a second EC2 host are extensions.

Core flow: checkout → lint/tests → image → optional publication → approval → candidate
check → cutover → live smoke check → archived deployment events.
This workshop has a deliberate human approval and therefore teaches continuous delivery.
Removing the gate later requires suitable release controls; it is not today's objective.

## Theory card 1: release identity and promotion

An image is the built application artifact. A tag is a human-readable reference that can
be overwritten. A digest/image ID identifies image content. Avoid relying on `latest`
to answer which revision is running.

Our tag combines Git revision and Jenkins build number. The Python deployment tool
resolves that tag to a local image ID once and uses that exact ID for candidate and live
containers. Moving to another host uses a registry and should pin the registry digest in
a hardened implementation. The current optional Ansible example uses the unique tag;
it assumes the workshop team does not overwrite it.

Build once and verify that artifact. Do not rebuild source between candidate and live and
assume the outputs are identical. Runtime configuration and persistent data are separate
from the image.

## Lab 1A: build the application image

Prerequisites: Day 1 green CI, Docker accessible to the agent user, Flask stopped on port
8000. Run these Bash commands on the dedicated lab host in this order:

```bash
.venv/bin/python scripts/preflight.py --docker
RELEASE_VERSION="$(git rev-parse --short=12 HEAD)-manual-1"
IMAGE_REF="workshop/task-api:$RELEASE_VERSION"
docker build --build-arg APP_VERSION="$RELEASE_VERSION" -t "$IMAGE_REF" .
docker image inspect "$IMAGE_REF" --format '{{.Id}}'
docker run -d --name workshop-api-manual -p 127.0.0.1:8000:8000 "$IMAGE_REF"
.venv/bin/python scripts/smoke.py --url http://127.0.0.1:8000 --version "$RELEASE_VERSION"
```

Expected: image build succeeds, image ID prints, and smoke returns health/version/tasks.
If Git reports “not a repository,” you are in the wrong directory or using an uninitialized
ZIP copy; initialize Git and commit the supplied files before deriving a revision.
Smoke retries allow startup time but eventually fail; they do not retry forever.

Inspect and remove only this disposable manual container:

```bash
docker logs --tail=50 workshop-api-manual
docker inspect workshop-api-manual --format '{{.Config.User}}'
docker rm -f workshop-api-manual
```

Expected user: `appuser`. The app runs under Waitress, not Flask's development server.
Removing this manual container frees port 8000. No persistent task data is expected from
this throwaway container because it was not mounted to the production volume.

## Theory card 2: smoke automation and Python error handling

`scripts/smoke.py` checks real HTTP responses at `/health`, `/version`, and `/tasks`.
It validates readiness, release identity, and a basic read route. It does not perform a
full end-to-end business transaction or prove every API feature works.
Retries are bounded (15 attempts, two seconds between failures, three-second request
timeouts). A slow startup has a chance to settle; a persistently unhealthy release fails.

`subprocess.run` in deployment uses argument lists instead of `shell=True`. Exit codes
are checked, operations have timeouts, and errors propagate to Jenkins. Reports are
written in `finally`, so failures leave evidence. The script contains recovery logic
rather than hiding failed operations with shell `|| true`.

Ask students to trace: what happens when Docker cannot be reached, when the candidate
fails, and when the new live container fails after replacing the old one?

## Lab 2A: deploy through the Python release tool

```bash
.venv/bin/python scripts/deploy.py --image "$IMAGE_REF" --version "$RELEASE_VERSION"
.venv/bin/python scripts/smoke.py --url http://127.0.0.1:8000 --version "$RELEASE_VERSION"
cat reports/deployment.json
docker ps --filter name=workshop-api
```

Expected event sequence for a first release: `image_resolved`, `candidate_verified`,
`live_verified`. A later replacement also records `previous_release_retained`.
The JSON has `ok: true`, the source image reference, content ID, version, and UTC event
timestamps. UTC timestamps permit comparison across machines; classroom times are local.

Run the same deployment command again. Expected: `already_deployed` and no replacement,
provided the running image ID matches and its smoke checks pass.

### Candidate → cutover → recovery

1. The candidate runs on localhost port 18080 with disposable data.
2. It must pass smoke checks for the requested version.
3. The old live container is stopped and retained as `workshop-api-previous`.
4. A new live container starts on port 8000 with `workshop-data` mounted at `/data`.
5. The live service must also pass smoke checks.
6. If cutover fails, the failed live container is removed and the old one is restarted.
   If restoring the old release also fails, the report explicitly records `recovery_failed`.

There is a short outage between stopping the old container and verifying the new one.
This is not blue/green traffic switching. A failed candidate leaves the existing live
container running. On the first-ever release there is no old release to recover to.
The tool retains only one prior container; archive release metadata separately if history
matters. It assumes exclusive ownership of its Docker names and ports on this host.

## Lab 2B: prove persistence across an application release

After the first automated deployment:

```bash
curl -fsS -X POST http://127.0.0.1:8000/tasks -H 'Content-Type: application/json' -d '{"title":"Must survive release"}'
RELEASE_VERSION="$(git rev-parse --short=12 HEAD)-manual-2"
IMAGE_REF="workshop/task-api:$RELEASE_VERSION"
docker build --build-arg APP_VERSION="$RELEASE_VERSION" -t "$IMAGE_REF" .
.venv/bin/python scripts/deploy.py --image "$IMAGE_REF" --version "$RELEASE_VERSION"
curl -fsS http://127.0.0.1:8000/tasks
```

Expected: the previously created task remains. The image changed; the volume did not.
This is a real persistence check, not a claim that the disposable candidate validates
the live database's contents.

### Theory card 3: application recovery vs database recovery

Restarting the old image does not undo new data or a database schema change. Our first two
days use the same compatible schema. Later modules should teach migration validation,
expand/contract changes, and backups. Do not add a destructive migration to this exercise
and assume the existing rollback will make it safe.

SQLite suits this small, single-host exercise. Its file database is not a substitute for
the later PostgreSQL/Kubernetes deployment design. Tests isolate data using temporary
files; releases persist it using a named Docker volume.

## Lab 3: Jenkins continuous delivery

Create a second Pipeline job `workshop-day2`, using the same repository and branch `*/main`.
Script Path: `pipelines/Jenkinsfile.day2`. Read the file with students before building.

1. First run with defaults. Jenkins may display **Build Now** before it has loaded the
   parameters; after the first run, use **Build with Parameters**.
2. Verify lint/tests/image build. Defaults do not deploy and do not push to a registry.
3. Run again with `DEPLOY=true`, `PUSH_IMAGE=false`, `INJECT_BAD_RELEASE=false`.
4. Review the image/version at the approval stage and approve within five minutes.
5. Inspect release events and download `reports/deployment.json` from build artifacts.
6. On the agent host, call `/version` and show that it matches the Jenkins release.

The entire pipeline uses one dedicated host so its built image exists where deployment
runs. Do not spread stages across unrelated agents without publishing/pulling an artifact.
`disableConcurrentBuilds` serializes this job; it does not lock other jobs. Use only one
deployment job per host for this workshop. The waiting approval holds the agent allocation,
which is acceptable for a small class but should be redesigned for larger installations.

### Optional registry exercise

Create a Docker Hub repository and an access token. In Jenkins → Credentials add a
username/password credential: username = Docker Hub username, password = access token,
ID = `dockerhub`. Use a token scoped to the required repository permissions.

Set `IMAGE_REPO=YOUR_DOCKERHUB_USERNAME/task-api` and `PUSH_IMAGE=true`.
The pipeline passes the token to `docker login --password-stdin`, avoids Groovy secret
interpolation, and stores the login in a temporary Docker config directory removed on exit.
Jenkins masking reduces accidental disclosure; it cannot make deliberately printed or
transformed secrets safe. See [Jenkins credentials](https://www.jenkins.io/doc/book/using/using-credentials/).

Verify the image/tag in the registry. For a separate remote host, use `docker pull` there.
The local deployment pipeline does not need registry credentials when `PUSH_IMAGE=false`.

## Lab 4: reject a bad release

First confirm a healthy live release and note its `/version`. Then run Jenkins with
`DEPLOY=true`, `INJECT_BAD_RELEASE=true`, and approve the lab attempt.
Alternatively build manually:

```bash
BAD_VERSION="$(git rev-parse --short=12 HEAD)-bad-1"
BAD_IMAGE="workshop/task-api:$BAD_VERSION"
docker build --build-arg APP_VERSION="$BAD_VERSION" --build-arg DEMO_BROKEN=1 -t "$BAD_IMAGE" .
.venv/bin/python scripts/deploy.py --image "$BAD_IMAGE" --version "$BAD_VERSION"
cat reports/deployment.json
curl -fsS http://127.0.0.1:8000/version
```

Expected: deployment exits nonzero; candidate logs/events are captured; the previous live
version remains available. Do not claim rollback occurred: the candidate was rejected
before the old live container was stopped. This distinction is part of the assessment.

The test suite's `test_failed_cutover_restores_previous` separately exercises recovery
after cutover with mocked Docker/HTTP boundaries. Run and inspect it:

```bash
.venv/bin/python -m pytest tests/test_automation.py -k 'cutover or candidate' -v
```

Advanced instructor exercise: simulate a live failure after candidate validation on an
isolated disposable host and examine `previous_release_restored`. Avoid editing live
deployment logic during the basic class. The mock test alone is not an executed Docker
rollback demonstration.

The instructor can also run `tools/verify_release.py` on a disposable host. It expects
images `workshop/task-api:validation-1`, `:validation-2`, and `:validation-bad`, built with
matching APP_VERSION values; the bad image uses DEMO_BROKEN=1. It checks persistence,
rejects the bad candidate, then injects DEMO_BROKEN=1 into only the new live container
to exercise actual Docker cutover/recovery. It deliberately replaces this host's workshop
containers and adds a marker task. See the validation record for the performed dry run.

## Stretch: use Ansible to deliver to a prepared EC2 host

This extension starts after the image is published. It reuses known Docker/Ansible skills;
it does not teach infrastructure provisioning. Run Ansible on Linux/WSL, not native Windows.

On the target: Ubuntu 24.04, Python 3, Docker, and `ubuntu` Docker access are prerequisites.
For a private image, securely log in to the registry on the target first. The playbook
does not transmit Jenkins registry secrets or provision EC2 resources.

On the control VM:

```bash
python3 -m venv .ansible-venv
.ansible-venv/bin/python -m pip install 'ansible-core>=2.17,<2.20'
cp infra/inventory.example.ini infra/inventory.ini
```

Edit `infra/inventory.ini`: replace the example IP. Set key permissions, validate SSH,
and accept the verified host key before Ansible runs:

```bash
chmod 600 /path/to/workshop-key.pem
ssh -i /path/to/workshop-key.pem ubuntu@YOUR_EC2_IP 'python3 --version && docker info --format "{{.ServerVersion}}"'
.ansible-venv/bin/ansible -i infra/inventory.ini workshop --private-key /path/to/workshop-key.pem -m ping
.ansible-venv/bin/ansible-playbook -i infra/inventory.ini infra/deploy.yml --private-key /path/to/workshop-key.pem -e "image_ref=YOUR_DOCKERHUB_USERNAME/task-api:YOUR_RELEASE_TAG release_version=YOUR_RELEASE_TAG"
```

Ansible copies the stdlib-only smoke/deployment scripts, pulls the image, and runs delivery
on the target. The app binds to target localhost. Verify remotely through SSH, or forward
another laptop port:

```bash
ssh -i /path/to/workshop-key.pem ubuntu@YOUR_EC2_IP 'curl -fsS http://127.0.0.1:8000/version'
```

Expected: release events print and version matches. `image_ref` and `release_version` must
describe the same image. A private-registry authentication failure happens before cutover.
Do not disable SSH host-key checking as a quick fix.

## Assessment

Demonstrate a healthy release, matching version, persistent task data, and rejected bad
candidate. Explain one actual error with evidence. Submit Jenkins build URL, commit,
image reference, and deployment report. Explain when previous-image recovery is possible,
why it does not restore a database, and what still needs improvement for production.
